# Ветки, коммиты и PR

`main` всегда собирается и проходит CI, поэтому напрямую в него не коммитим. Любая работа идёт в короткой ветке и вливается через PR. На `main` включена защита: нужен PR и зелёные проверки.

- `backend` из [backend.yml](../.github/workflows/backend.yml): формат кода, сборка, актуальность OpenAPI-документа и тесты.
- `frontend` из [frontend.yml](../.github/workflows/frontend.yml): актуальность клиента API, линтер, тесты и сборка.
- `conventions` из [conventions.yml](../.github/workflows/conventions.yml): имя ветки, заголовок PR и сообщения коммитов.

Пока бэкенда или фронта нет в репозитории, их проверки проходят сразу и пишут в логе, что проверять пока нечего.

## Как назвать ветку

Шаблон такой: `<тип>/<область>-<суть>`, а если есть issue, то `<тип>/<номер>-<область>-<суть>`.

```
chore/backend-skeleton
feat/auth-login
feat/schedule-week-view
feat/12-requests-status-timeline
fix/grades-session-countdown
docs/readme-demo-accounts
spike/frontend-pwa-offline
```

| Тип | Когда |
|---|---|
| `feat` | новая возможность |
| `fix` | исправление ошибки |
| `refactor` | переделка без изменения поведения |
| `test` | только тесты |
| `docs` | README, документация, AGENTS.md |
| `ci` | GitHub Actions |
| `chore` | каркас, зависимости, настройки, Docker и прочая инфраструктура |
| `spike` | прототип или эксперимент. Обычно его не вливают, итогом становится вывод, а код потом пишется начисто |

| Область | Что затрагивает |
|---|---|
| `auth`, `profile`, `schedule`, `grades`, `requests`, `notifications`, `today`, `staff` | раздел кабинета целиком: API, экран и тесты |
| `api` | `Program.cs`, middleware, обработка ошибок |
| `db` | `DbContext`, миграции, сиды |
| `ui` | UI-кит и дизайн-токены |
| `backend`, `frontend` | бэкенд или фронт целиком: каркас, сборка, общие настройки, роутер |
| `deploy` | compose, Dockerfile, nginx, скрипты |
| `readme`, `product`, `architecture`, `contributing`, `design`, `ai` | документация. `ai` это `AGENTS.md`, субагенты и `docs/ai/` |

В имени ветки только латиница в нижнем регистре, цифры и дефисы, без кириллицы, пробелов и `_`. Суть это 2-4 английских слова о том, что именно делаем: `schedule-week-view` хорошо, а `yaroslav-work` или `fix-2` плохо, по ним через неделю никто не вспомнит, что там было.

Новый раздел кабинета получает свою область, например `assistant` для ИИ-помощника или `appointments` для записи на приём.

Если фича задевает и API, и экран, она всё равно живёт в одной ветке, а область у неё по разделу, например `feat/requests-new-request-form`. Область `frontend` оставляем для того, что ни к какому разделу не привязано.

Облачные агенты иногда создают ветки сами, со своими префиксами: `claude/`, `copilot/`, `cursor/`, `codex/`, `gemini/`. Такие ветки тоже разрешены, но заголовок PR из них всё равно пишется по шаблону ниже.

## Как назвать коммит и PR

Коммиты и PR называем по одному шаблону: `<тип>(<область>): <что сделано>`. Тип и область берём из имени ветки, но без сути и без номера issue. Для ветки `chore/backend-skeleton` префикс будет `chore(backend):`, для `feat/12-requests-status-timeline` будет `feat(requests):`.

После двоеточия пишем по-русски, с маленькой буквы и без точки в конце. Описываем результат, то есть что появилось или изменилось, а не процесс: "переносы пар видно прямо в карточке" хорошо, а "добавил переносы" или "работа над расписанием" хуже. Названия библиотек, классов и команд оставляем как есть, по-английски. Хорошо, если заголовок укладывается примерно в 72 символа: дальше его обрезают и GitHub, и `git log --oneline`.

### Коммиты в ветке

Все коммиты в ветке начинаются с того же префикса, что и сама ветка, а текст после двоеточия рассказывает про конкретный шаг. Даже мелкие правки называем по шаблону и пишем, что именно поправили. Если какому-то коммиту хочется дать другой тип или другую область, скорее всего, эта работа просится в отдельную ветку.

### Заголовок PR

У PR тот же префикс, а текст после двоеточия обобщает все коммиты ветки и отвечает на вопрос "что даёт эта ветка целиком". Вливаем через Squash and merge, так что заголовок PR становится единственным коммитом в `main`, и по нему потом читают историю проекта.

Например, в ветке `feat/requests-status-timeline` могли быть такие коммиты:

```
feat(requests): история статусов заявки в API
feat(requests): таймлайн статусов на экране заявки
feat(requests): где и когда забрать справку
```

А заголовок PR их обобщает:

```
feat(requests): статус заявки виден как трекинг посылки
```

Заголовки вроде `fix`, `правки`, `WIP` или `feat(schedule): обновление` не годятся: по ним через месяц никто не поймёт, что изменилось. `Feat(Schedule): Added week view` тоже не подходит, тут сломан шаблон: тип и область пишем строчными, а текст по-русски.

В описании PR по шаблону пишем, что сделано, как проверяли и что сделал ИИ. Блок про ИИ потом почти целиком уходит в описание процесса для жюри, так что лучше заполнять его сразу.

## Как вливаем

Одна ветка решает одну задачу и превращается в один PR. Ветка живёт дни, а не недели, создаётся от свежего `main` и удаляется после слияния.

PR вливает тот, кто его открыл, как только проверки зелёные. Владелец репозитория может влить PR и с красными проверками, но это только на крайний случай, например CI сломался за час до дедлайна.

Перед слиянием стоит ещё раз перечитать заголовок PR: пока шла работа, ветка могла подрасти, и он должен описывать то, что в итоге в неё вошло.

## Правила в GitHub

Правила для веток лежат в [.github/rulesets/](../.github/rulesets/) в виде JSON, их импортируют в настройках репозитория: Settings, Rules, Rulesets, New ruleset, Import a ruleset.

| Файл | Что делает |
|---|---|
| `main.json` | защищает `main`: нельзя удалить ветку и переписать историю, нужен PR, проверки `backend`, `frontend` и `conventions` зелёные, ветка свежая относительно `main`, вливаем только через squash |
| `branch-names.json` | не даёт создать ветку, имя которой не начинается с разрешённого типа или префикса агента |

Ещё в Settings, General стоит оставить только Allow squash merging и включить Automatically delete head branches.

Проверить формат коммитов и PR правилами GitHub на обычном аккаунте нельзя, это доступно только в Enterprise. Поэтому формат проверяет workflow `conventions`, а `main.json` требует, чтобы он был зелёным. Скрипт можно запустить и локально, до пуша:

```bash
python3 .github/scripts/check_conventions.py \
  --branch feat/schedule-week-view \
  --title "feat(schedule): расписание на неделю со свайпом по дням"
```

Если правило мешает работать, его меняют отдельным PR с типом `ci` или `docs`, а не обходят.
